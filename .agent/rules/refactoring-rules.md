# 대규모 리팩토링 및 코드 변경 프로토콜 (Refactoring Rules)

이 문서는 프로젝트의 대규모 아키텍처 변경, 모듈 분리, 전체 코드 리팩토링 및 리뷰 후 수정 작업 시 에이전트가 준수해야 할 필수 워크플로우를 정의합니다.

## 1. 사전 분석 및 안전 점검 (Mandatory Graph-First Workflow)
*   **[HARD REQUIREMENT] 그래프 선제 호출**: 리팩토링이나 모듈 분리를 계획(#PLAN)하기 전, 에이전트는 **절대 `grep`이나 `read_file`로 먼저 접근하지 마십시오.**
*   **필수 도구 체인**: 분석의 시작은 반드시 다음 도구 호출이어야 합니다.
    1. `mcp_code-review-graph_build_or_update_graph_tool` (최신 상태 동기화)
    2. `query_graph_tool(pattern="callers_of")` 또는 `get_impact_radius_tool` (의존성 전수 조사)
*   **사후 땜질식 검색 금지**: 리팩토링으로 인해 파생되는 연결 지점(Links, Method Calls, Events)은 사후에 버그가 터졌을 때 `grep`으로 찾아서 수정하는 것이 아니라, **사전 그래프 분석 단계에서 모두 찾아내어 체크박스 태스크로 미리 올려두어야 합니다.**
*   **계획서 필수 포함 사항**: 모든 `#PLAN` 문서의 첫 번째 섹션은 반드시 **"지식 그래프 의존성 분석 결과"**여야 합니다. 해당 도구의 원본 출력(또는 핵심 요약)을 포함하지 않은 계획은 무효로 간주하며, Jerry님은 이를 근거로 작업을 반려할 수 있습니다.
*   **MCP Graph Root**: `repo_root` 매개변수는 반드시 `gemini-cli-wrapper/`로 설정하여 노이즈를 차단하십시오.
*   *(예외 조항)*: 순수 JavaScript의 동적 타이핑 한계로 인해 지식 그래프가 특정 메서드의 호출부를 100% 식별하지 못할 경우에 한해서만 보조적으로 `grep`을 사용할 수 있으며, 이때는 반드시 문서에 사유를 명시해야 합니다.


## 2. 고해상도 설계 및 계획 (#PLAN)
*   **[MANDATORY] 컨텍스트 동기화**: PLAN 또는 IMPL 문서를 생성했다면, 즉시 **`context.md`의 To-Do 리스트에 해당 항목을 등록**하십시오. 이는 세션 간 작업 누락을 방지하기 위한 필수 절차입니다.
*   **인과 관계 명시**: 단순히 "파일을 분리한다"가 아니라, **[무엇을] [어디로] 옮기며, [기존 코드와 어떻게 연결되는지]**에 대한 인과 관계를 상세히 기술해야 합니다.
    *   **Source -> Destination Mapping**: 특정 함수/클래스가 어떤 파일에서 어떤 파일로 이동하는지 명시.
    *   **Interface Connection**: 분리된 모듈이 기존 메인 파일과 어떤 API/Event/Import 방식으로 통신하는지 기술.
*   **체크박스 기반 태스크 세분화**: 모든 리팩토링 계획은 `PLAN` 또는 `IMPL` 문서 내에 **원자적 단위의 체크박스(`- [ ]`) 목록**으로 작성되어야 합니다.
    *   단순히 "리팩토링 완료"가 아닌, "A 함수 추출", "B 모듈 생성", "C 참조 업데이트"와 같이 검증 가능한 최소 단위로 쪼개어야 합니다.

## 3. 원자적 워크플로우 및 체크포인트 (Atomic Workflow & Checkpoints)
*   **단계별 수정 및 추적**: 한 번에 한 개의 체크박스 항목만 처리하는 것을 원칙으로 합니다.
*   **[Checkpoint Protocol]**: 각 체크박스 항목(Atomic Step)의 코드 수정 및 린트 검증이 완료되면 즉시 작업을 멈추고 Jerry님께 다음을 보고합니다:
    1. **진행 상태 업데이트**: `IMPL` 문서의 해당 항목을 `- [x]`로 마킹하고 현재 위치 보고.
    2. **수정 내역 요약**: 이번 단계에서 이동/변경된 구체적인 로직 요약.
    3. **테스트 가이드**: Jerry님이 해당 변경 사항이 기존 기능을 깨뜨리지 않았는지 확인할 수 있는 구체적인 방법.
    4. **다음 태스크 예고**: 리스트의 다음 체크박스 항목 안내.
*   **중단 및 대기**: Jerry님의 승인이 있을 때까지 절대 다음 체크박스 항목으로 넘어가지 않습니다.

## 4. 자체 검증 및 기록 (Self-Verification)
*   **린트(Lint) 강제 실행**: 수정 직후에는 반드시 프로젝트 루트에서 `.agent/tools/run_lint.sh` 명령어를 실행하여 문법 무결성을 자체 검증하고 결과를 로깅해야 합니다. 에러 발생 시 즉시 수정하십시오.
*   **Audit Trail 기록**: 위 스크립트를 실행하면 `lint_history/YYMMDD-HHMM-lint-check.log` 파일로 린트 결과가 자동 저장되어 작업의 안정성을 증명할 수 있습니다.
*   **상태 동기화**: `chat_history/`의 관련 문서 상태를 실시간으로 업데이트하여 작업의 진행도를 투명하게 관리하십시오.
