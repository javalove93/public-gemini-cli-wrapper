# Gemini CLI 모바일 액세스 (Telegram 봇 연동) 설계서

## 1. 개요 (Overview)
본 설계 문서는 모바일 환경에서 Telegram 메신저를 통해 데스크톱의 Gemini CLI 세션에 접근하고 제어하기 위한 아키텍처를 정의합니다. 기존 Child Process 제어 방식의 불안정성(파싱 오류, 데드락 등)을 해결하기 위해 **파일 시스템 기반의 비동기 메시징 구조(File-based Asynchronous Messaging)**를 채택합니다.

## 2. 아키텍처 (Architecture)

### 2.1. 통신 매개체 및 디렉토리 구조
데이터 전달의 안정성과 확장성을 위해 단일 `inbox` 디렉토리 규칙을 사용하며, 텍스트 대신 Markdown(`.md`) 포맷을 사용하여 AI의 구조적 데이터 처리와 Telegram의 네이티브 마크다운 렌더링 이점을 극대화합니다.

```text
project_root/
└── inbox/
    ├── in.md        # Bot이 작성하고 Gemini CLI가 읽는 요청 메시지
    ├── out.md       # Gemini CLI가 작성하고 Bot이 읽는 응답 메시지
    └── files/       # 모바일에서 업로드된 이미지, PDF, 문서 저장소
```

### 2.2. 데이터 플로우 (Data Flow)
1. **요청 수신:** 사용자가 Telegram 앱을 통해 텍스트나 파일(이미지/문서)을 전송합니다.
2. **요청 기록 (Bot -> File):** 
   - 봇 데몬은 수신된 파일을 `inbox/files/` 폴더에 저장합니다.
   - 텍스트 메시지와 파일 참조 경로(예: `![이미지](./files/photo.png)`)를 조합하여 `inbox/in.md`에 작성합니다.
   - 봇은 `inbox/out.md` 파일의 생성 및 변경을 감시(Polling/Watch)하기 시작합니다.
3. **AI 처리 (File -> Gemini):**
   - Gemini CLI는 `in.md` 파일의 변경을 감지하고 내용을 읽어들입니다. (감지 방식은 백그라운드 셸 스크립트 또는 전용 스킬로 구현)
   - 첨부된 파일이 있을 경우 `read_file` 도구를 사용하여 내용을 분석합니다.
   - AI가 요청된 작업을 수행합니다.
4. **결과 응답 (Gemini -> File):**
   - 작업 결과를 마크다운 형식으로 `inbox/out.md`에 기록합니다.
5. **결과 전송 (File -> Bot -> User):**
   - 봇 데몬이 `out.md` 변경을 감지하여 텍스트를 읽어옵니다.
   - Telegram API를 통해 사용자에게 마크다운 서식이 적용된 응답을 전송합니다.
   - 처리가 완료된 `in.md`, `out.md` 및 `files/` 내부 항목을 초기화(삭제 또는 아카이빙)하여 다음 요청을 준비합니다.

## 3. 주요 설계 결정사항 (Trade-offs & Decisions)

* **통신 포맷으로 Markdown(.md) 선택:** 
  단순 `.txt`나 복잡한 메타데이터 `.json` 대신 `.md`를 선택. 자연어 처리에 강한 LLM에게 친숙하며, Telegram 메신저 출력 시 코드 블록이나 표가 깨지지 않고 네이티브하게 렌더링됩니다.
* **통합 Inbox 디렉토리:**
  이미지용 폴더, 문서용 폴더를 따로 분리하지 않고 `inbox/files/`로 통합하여 봇 구현 로직을 단순화하고, AI가 탐색해야 할 범위를 한정지어 컨텍스트 낭비를 줄입니다.
* **비동기 파일 감시:**
  프로세스를 직접 물고 있는 것이 아니므로, Gemini CLI가 재시작되거나 에러가 발생해도 Bot 프로세스는 죽지 않고 유연하게 복구 가능합니다.

## 4. 미해결 과제 및 향후 구현 논의점 (TBD)
* **감시자(Watcher) 구현 방식:** Gemini CLI 내에서 `in.md`의 변경을 지속적으로 감시할 주체(예: 단순 bash 폴링 스크립트 vs Gemini CLI 고유의 Custom Skill)의 최종 결정 및 구현.
* **대용량 파일 처리:** 텔레그램 봇 API의 파일 다운로드 용량 제한(기본 20MB) 처리 방안.
* **다중 사용자 제어:** 본 설계는 단일 사용자(Admin)를 가정함. 다중 요청에 대한 Lock/Queue 메커니즘 필요 여부 검토.
